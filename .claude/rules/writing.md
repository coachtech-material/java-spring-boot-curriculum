# 執筆ルール

## 1. 文体

### トーン

- **本文**: 落ち着いた敬体で丁寧に解説する。過度に個人的な語りかけ（「率直に言うと」等）は避ける
- **🧠 先輩エンジニアの思考プロセス**: 実体験ベースの語りをここに集中させる。本文より口語的な表現を許容するが、「率直に言うと」「正直に言うと」等の前置きや読者を試す表現は避け、具体的な失敗談・設計判断の裏話・実務のあるあるで語る

> 📝 **先輩エンジニア** （メンター人格）: Java / Spring を実務で長年扱うベテラン。PHP / Laravel でキャリアを積んだ後に Java へ移った経歴を持ち、深い Java の知見と「Laravel から来た人」の感覚を併せ持つ。型や DI でつまずいた当時の実感と、現場で鍛えた設計判断の両面から語れるのが強み。

### 用語・表記

- 敬体（です・ます調）で統一。読者への呼びかけは「あなた」
- 読者を指す語は「あなた」「学習者」を用い、特定の制度名・組織名（受講区分・所属エージェント名など）は本文で使わない
- ダッシュ記号（`——`、`—`、`–`）は使わない
- Java / Spring Boot の用語は参考資料（公式ドキュメント）の表記に従う。範囲外の内容は WebSearch / WebFetch で裏付ける
- 時間経過で変わる情報は最新情報を取得し「○○時点」と日付を明記
- 外部ソースを参照する場合は出典を明記する
- `**太字**` は語句・キーフレーズに限定する。文全体を太字にしない。💡 / 🔑 / 📝 プレフィックス付きの行でも同様（❌ `💡 **○○は△△です。**` → ✅ `💡 ○○は **△△** です。`）
- Markdown の `**text**` は閉じ `**` 直後にスペースなしで日本語が続くと適用されない。`**○○** の場合` のようにスペースを入れる。全角括弧 `（` も同様: `**○○**（補足）` → `**○○** （補足）`

| 表記 | 備考 |
|---|---|
| セクション | 教材本文ではカタカナ表記。内部ドキュメントでは英語 |
| Spring Boot / Spring Framework | 製品名は英語表記。バージョンは「Spring Boot 4.0.x」のように明記する |
| DI / IoC / JPA / JWT / REST / ORM | 略語は英大文字。初出時に正式名称を併記する（例: DI（依存性注入）） |
| アノテーション | 一般語はカタカナ。コード上の記述は `@RestController` のようにコード表記する |
| Bean / エンティティ / リポジトリ / コントローラ | 概念を指すときはカタカナ（Bean は英語可）。コード上の型・クラス名は英語・コード表記する |
| Laravel 用語（Eloquent・Blade・Artisan 等） | 対比で用いる際は Laravel 公式の表記に従う |

### 絵文字

| 絵文字 | 用途 |
|---|---|
| 🎯 | 学習目標（Section 冒頭） |
| ✨ | まとめ（Section 末尾） |
| 💡 | TIP・補足 |
| ⚠️ | 注意事項・よくあるエラー |
| 📝 | ノート・定義・補足説明 |
| 🔑 | 重要概念・キーポイント |
| 🏃 | ハンズオン手順・実践 |
| 🧠 | 経験者の視点・思考プロセス |
| 📌 | 操作前の確認事項 |
| ✅ | 完成チェックリスト（ハンズオン・混合） |
| 📖 | この Chapter の進め方（2層以上の場合） |

## 2. 構造

### Section の種類

| 種類 | 内容 |
|---|---|
| **概念** | 意義・仕組み・使い方を解説 |
| **ハンズオン** | 概念で学んだ機能を実践。冒頭に概念 Section への逆リンク |
| **混合** | 概念を学びながらすぐに手を動かす |

### 見出しの設計

**Why → What → How**（抽象→具体）の流れで組む。

### テンプレート

全 Section 共通の骨格に、種類ごとの差分を組み合わせる。

```markdown
# [セクション番号] セクションタイトル

<!-- 前提がある場合: 📝 **前提知識** 行を挿入 -->
<!-- 概念（グループ先頭）の場合: グループ全体像を挿入 -->
<!-- ハンズオンの場合: 📝 **このハンズオンで使う機能** 行を挿入 -->

## 🎯 このセクションで学ぶこと

- 学習目標1
- 学習目標2

[1文で Section の流れを示す]

---

## 導入: [課題・痛みから入る見出し]

### 🧠 先輩エンジニアの思考プロセス

> [実務の経験に基づいて自由に語る]

---

<!-- 本文: 種類ごとに異なる（「種類ごとの差分」を参照） -->

---

## ✨ まとめ

- ポイント1
- ポイント2

---

次のセクションでは、[次の内容への接続]。
```

**次セクションへの接続**:
- プレーンテキストで記述する（Markdown リンクやカギ括弧は使わない）
- **次セクションへの接続文** は、OUTLINE.md の次セクションのゴールに含まれるキーワードを漏れなく含める
- **Chapter 最終セクション**: Chapter の学びの振り返り + 次の Chapter への橋渡し
- **Part 最終セクション**: 上記に加え、Part 全体の振り返り + 次の Part への橋渡し
- **教材全体の最終セクション**: 教材全体の締め括り文を記述する（学んだことの振り返り + 次のステップへの示唆）

### 種類ごとの差分

**概念**:

- 本文は `## 見出し` で構成する
- 2層以上の場合、親グループの最初の Section のみ、タイトル直後にグループ全体像を含める。種類が混合でもグループ先頭であれば同様に含める。グループ全体像は `##` 見出しを使わず、タイトル直後に直接記述する。構成: ① 概要文（1-2文）② セクション一覧テーブル（セクション / テーマ / 種類）③ `📖 **この Chapter の進め方**: [学習の流れ]`

**ハンズオン**:

- タイトル直後に `📝 **このハンズオンで使う機能**: [機能名]（[セクション名] で学習）` を挿入
- 導入の後に `## 📌 [作業名]前の確認`（チェックリスト形式）を挿入
- 本文は `## 🏃 実践: [タイトル]` の中に `### 🏃 Step N: [タイトル]` の連番で構成する
- 本文の後、まとめの前に `## ✅ 完成チェックリスト` を挿入
- 長いコードは `<details>` で折りたたむ

**混合**:

- 本文の前半は `## 見出し`（概念解説）で構成する
- 本文の後半は `## 🏃 実践: [タイトル]` の中に `### 🏃 Step N: [タイトル]` の連番で構成する
- 本文の後、まとめの前に `## ✅ 完成チェックリスト` を挿入

**エラーフォーマットの使い分け**:
- エラーメッセージ（コードブロック）を伴う場合 → blockquote 形式（下記テンプレート）
- エラーメッセージなしの一般的な注意 → `⚠️ **注意**: ...` でインラインに記述

> ⚠️ **よくあるエラー**: [概要]
>
> ```
> [エラーメッセージ例]
> ```
>
> **原因**: [なぜ発生するか]
>
> **対処法**: [解決手順]

---

## 3. コンテンツ

### コードの見せ方

- コードを含む場合、コードブロック上部にファイルパスをコメントで明示する。コメント構文は言語タグに合わせる:
  - `java` / `typescript` / `javascript` / `php`: `// filepath`
  - `xml`: `<!-- filepath -->`
  - `sql`: `-- filepath`
  - `yaml` / `properties` / `dockerfile` / `bash`: `# filepath`
  - `tsx` / `jsx`: `{/* filepath */}`
  - `css`: `/* filepath */`
- コードブロックには必ず言語を指定する。非コードコンテンツ（ディレクトリツリー、コマンド出力等）には `text` を使用する
- diff 表示は使わない（テキストで説明し変更後のコードを示す）
- **参考資料のコードを引用する場合は正確性を最優先する**。コードを簡略化して掲載する場合は、コードブロックの直前に「以下は主要部分の抜粋です」と明記し、省略した重要な処理を本文で補足する。ファイルパス・変数名・設定値は実ファイルと完全に一致させる
- 本教材で主に使う言語タグ: `java`、`xml`（pom.xml 等）、`yaml` / `properties`（application.yml / *.properties）、`sql`、`bash`、`text`

### 解説の深さ

- OUTLINE.md に前提（`前提:` フィールド）が記載されている場合、🎯 の前に `📝 **前提知識**: このセクションは○○の内容を前提としています。` と明記する
- 前提知識（概念）は概念の再入門を省略する。ただし読者の Java 知識はゼロのため、Java / Spring Boot での具体的な実現（記法・型・作法・差異）は省略せず解説する。基本文法も Java での書き方は必ず扱う。既習との差異・組み合わせ時の注意点は特に丁寧に
- Java / Spring Boot 固有の概念は初出時に丁寧に解説し、2回目以降は初出 Section への参照
- 同じ概念を別の箇所で繰り返さない
- 導入は「これがないと何が困るか」（課題）から入る
- 処理の流れや構造は図で視覚化する。図は **Mermaid** を主体とする（フロー図・シーケンス図・クラス関係図・ER 図など）。Mermaid が描画されない箇所のみ ASCII 図で代替する
- 未説明の用語をツリーやリストに含める場合は、簡潔なコメントか後続セクションへの参照を付ける
- つまずきポイントを先回りする（⚠️ で説明）
- 先の Section で扱う内容は「今は概要だけ把握すれば十分です」と明記する
- 初回リリースでは画像を含めず `<!-- TODO: 画像追加 - ○○の画面 -->` でプレースホルダーを残す。TODO コメントの画面名は実際の表示と一致させる（例: 自動ログインされる画面に「ログイン画面」と書かない）
- Section あたりの目安文字数: 最低 4,000 文字（概念主軸・Laravel 対比・Why→What→How で丁寧に解説するため）

### バージョン差分の扱い（案件接続の要）

読者が入る案件は Java / Spring Boot のバージョンがまちまちなので、**学んだ書き方がそのまま現場で通用すること** を最優先する。バージョン差分は本文を散らかさず、必要な箇所で短いコラム（💡 / 📝）として補足する。

- **Java**: コードは **17 で通用する書き方** を基本とする（record・Optional・Stream は 17 から使えるので通常どおり用いる）。Java 21 専用機能（仮想スレッド・switch のパターンマッチング・record パターン等）を使う場合は「これは Java 21 からの機能」と明示する。`var`・record・switch 式など旧 LTS（8 / 11）で書き方が異なるものは差分コラムを添える。
- **Spring Boot**: **4.0.x をメイン** に書く。ただし現場遭遇率は 3.x が高いため、要所で次を補足する。
  - **3.x への読み替え**: Jackson（4.0 は Jackson 3 / `tools.jackson`、3.x は Jackson 2 / `com.fasterxml.jackson`）、設定キーや一部 API の差
  - **2.x → 3.x の移行**: `javax.*` → `jakarta.*` の名前空間（レガシー案件で `javax` を見たときに気づけるように）

コラムの書き方の例:

> 💡 **Spring Boot 3.x ではこう書きます**: 本教材は 4.0.x（Jackson 3）を前提にしています。3.x 案件では Jackson 2 を使うため、import が `com.fasterxml.jackson.databind.ObjectMapper` に変わります（挙動はほぼ同じ）。

### 実践パートの品質

🏃 実践・ハンズオンを含む Section では、以下を守る:

- **手順の再現性を保証する**: 各ステップを記載どおりに実行した場合に期待する結果が得られることを、実際の動作から確認する。特に Git 操作（`git checkout`, `git restore`, `git reset` 等）は、ステージ状態・ブランチ状態を正確に追跡し、クリーンアップ手順まで含める
- **前提状態を明示する**: 各ステップの実行前に必要な状態（コンテナ起動済み、特定ブランチにいる等）を `📌` チェックリストで示す
- **副作用のクリーンアップ**: 実践で作成したブランチ・コミット・ファイル変更は、セクション末尾で元に戻す手順を必ず含める

### コピペで完成するハンズオンの留意点

総合ハンズオン（Part 5）のように、複数 Section をまたいで **1 つの成果物を積み上げる** ハンズオンでは、「学習者が最初の Section から順に、各コマンド・コードをそのままターミナル / IDE にコピペして進めると成果物が完成する」ことを保証する。各 Section の境界でコンパイル / 実行が通ることを前提に、次を必ず守る。

**コードはコピペでコンパイル / 実行が通る形にする**

- getter / setter などの定型コードを「IDE で生成」に委ねず、**省略せず全掲載** する。後続 Section がそのメソッドを呼ぶなら、揃っていないとビルドが通らない（IDE での生成方法は補足に留める）
- **前方参照しない**: 各 Step のコードは、その時点で既に定義済みのものだけを参照する。動作確認より後の Step で追加するメソッドを先に呼ばない（例: N+1 は、まず素朴なメソッドで動かし、後の Step で fetch join に差し替える順序にする）
- 「既存ファイルに追加 / 置換」する Step では、**どのファイルのどこへ** 入れるか（import はファイル先頭、メソッドはクラス内、メソッド全体を差し替え 等）を明示し、**新規に必要な import だけ** を示す（既に import 済みのものを再掲して混乱させない）

**足場（環境・配置）の手順を省略しない**

- プロジェクトのディレクトリ作成・展開・`cd`・**IDE で開く操作**・パッケージ用フォルダ作成・ファイルの配置先を省略しない。各コマンドの **実行場所（カレントディレクトリ）を毎回曖昧にしない**
- OS 差を補足する（例: `./mvnw` は Windows では `mvnw`）。初出で一度示し「以降も同様」と添える

**動作確認は実際の挙動と一致させる**

- レスポンス本文が無い成功（`201` 等）は `curl -i` でステータスを可視化する
- 出力例（ソート結果・JSON のフィールド順・ログ）は、掲載したコードを実行したときの **実際の結果** と一致させる。憶測で書かない
- ブラウザ確認では、想定どおり起きる中間状態（認証必須パスで `401` になる 等）を「正常です」と明記し、非同期処理は結果の確認方法（`await` してステータス表示 等）まで示す
- Docker で複数サービスを起動する場合、`depends_on` だけに頼らず DB 等の準備完了を待つ（`healthcheck` + `condition: service_healthy`）

**フレームワークの挙動は裏取りしてから断定する**

- 「このコードで動く」「このスターター名で解決する」が成否を分ける箇所（スターター / 依存名、テストスライスが読み込む Bean、アノテーションの要否、バージョン専用機能 等）は、公式ドキュメント等で **対象バージョンでの挙動** を確認してから書く

**コードを書かない設計 Section の表現**

- 設計だけで成果物（ファイル）が生まれない Section では、「完成チェックリスト」「成果物が揃っている」といった表現を避け、「設計を説明できる / 決められた」など **理解・意思決定** として書く。冒頭の `📝` も「使う機能」ではなく「活かす概念」等、コードを書かない実態に合わせる

### 任意ハンズオン枠（Part 1〜2 の JShell トラック）

Part 1〜2 の概念 Section には、希望者が手を動かせる **任意の JShell ハンズオン枠** を添える（対象 Section は OUTLINE.md の「設計方針」を参照）。概念主軸を崩さないための書式を定める。

**配置と基本姿勢**

- 概念 Section の本文の後、`## ✨ まとめ` の直前に `## 🏃 手を動かす: [一言タイトル]` を置く
- 枠の冒頭で **「読み飛ばしても本筋の理解に支障はない」** ことを 1 文で簡潔に示す（見出しに既に「（任意）」が付くので、「手を動かすと腹落ちする」等の動機説明は盛らずに短くする）
- 起動方法・JShell の操作は **1-1-4 に集約** し、各枠では「1-1-4 の手順で JShell を起動し、以下を貼り付けます」と参照する（Docker コマンドや操作を毎回再掲しない）

**お題の作り方（入力と出力の見せ方）**

- お題はその Section の **「概念の一番おいしい 1 点」に絞る**（網羅しない。長くても十数行でコピペして動く範囲）
- **独立した式・短い文**（`7 / 2`、確認の `names` など）は `jshell>` 形式で 1 つずつ示す（`jshell>` の行が入力、その下が出力）。**複数の独立式を 1 ブロックにまとめない**（セミコロンなしの式を並べて貼ると JShell が 1 文と誤解してエラーになる）
- **1 つの複数行コード**（クラス定義・`try`・`switch` 代入・`stream` チェーン）や **`;` 付き文の列**は、`jshell>` を付けない `java` ブロックで示す（`{ }` で閉じる 1 単位、または `;` 区切りはブロックごと貼り付けられる）。直前に「次のブロックを貼り付けます」、出力は別の `text` ブロックに「次のように表示されます」と添え、入力と出力を区別する
- 枠の冒頭で「`jshell>` が入力、その下が出力」と一言示す
- 出力は憶測で書かず、Docker + JShell（`eclipse-temurin:21`）で **実機検証した実際の結果** と一致させる。`$N` の連番は実機の記載順の値を載せてよいが、`at (#N:1)` のような環境依存の行番号や `Task@47c62251` のハッシュは「実行のたびに変わる」と添える
- 静的型付けの体感には「わざと壊して直す」（型の合わない代入でエラーを見る等）を 1 つ入れると効果が高い
- `/reset` でクラスを定義し直すなど JShell コマンドを使う場合は本文で指示する（`.jsh` ファイルに書いて `/open` する方法を補足してもよい）

**JShell の限界は正直に書く**

- JShell で再現できない事項は枠内で深追いせず、「ここは JShell では扱わない（理由）。本筋は本文 / Part 5 で」と明示する。主なもの:
  - **検査例外のコンパイルエラー**: JShell はトップレベルで検査例外を自動緩和するため、「`catch` か `throws` が必須」というコンパイルエラーは再現されない（1-3-2）
  - **1 ファイル 1 クラス・パッケージ＝ディレクトリの規約**: JShell はファイルレスの REPL のため体感できない（2-1-1 ほか。Part 5 で実ファイルとして扱う）
- 初回起動時の `INFO: Created user preferences directory.` は「無視してよい」と添える（つまずき先回り）
